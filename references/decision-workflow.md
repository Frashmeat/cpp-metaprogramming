# 功能级判断流程

在较大功能、多个职责相互影响或技巧选择依据不清时读取。局部任务按 [主技能](../SKILL.md) 的简版流程处理。这里规定判断依据，不要求每次创建方案文档或完成固定数量的步骤。

## 1. 确定任务和契约

| 任务 | 调查与输出重点 |
|---|---|
| 解释/局部选型 | 当前问题对应什么技巧、适用条件和收益 |
| 设计/实现 | 功能契约、职责划分、技巧组合及验收 |
| 故障诊断 | 先复现，再定位查找、推导、替换、约束、实例化或运行行为 |
| 性能诊断 | 先建立可比较基线，再选择改动 |
| 只读审查 | 沿实际调用路径检查已有选择，输出证据和影响，不默认重写 |

从需求、调用点和构建配置确认：输入输出、允许与拒绝的行为、可调整范围、兼容目标、工具链，以及已有元数据/traits/测试。区分事实、假设和未知项；能调查的事实自行取得，会改变公开接口、支持范围或整体设计的缺失要求才向用户确认。

## 2. 区分计算对象与阶段

| 判断问题 | 进入的路径 |
|---|---|
| 需要查询/产生类型，还是只计算一个值？ | 类型计算使用模板等；普通值算法先考虑普通函数/constexpr |
| 需要限制接口，还是选中接口后分类处理？ | 前者考虑 concepts；后者考虑 if constexpr、重载等 |
| 输入何时可知，是否必须静态检查？ | 区分可常量求值与必须立即求值 |
| 多个元素是否类型不同，结果是否需要保留静态类型？ | 参数包、tuple/apply、类型列表等 |
| 是否有多个操作依赖同一份结构描述？ | 先复用元数据，必要时比较可用反射 |
| 只有运行期才知道类型集合、值或配置？ | 保留相应动态处理，静态生成仅负责已知部分 |

普通实现、标准库或项目组件已满足目标时，选择不增加元编程。代码外观相似不代表语义相同；不能只为去重就把不同职责压入大量策略参数。

## 3. 按职责拆分较大功能

沿输入到输出的实际路径识别职责，不先设“模板层”“constexpr 层”。只有确实影响选型的子功能才单列。

每个子功能明确：

| 内容 | 要得到的信息 |
|---|---|
| 职责与契约 | 处理什么、支持什么、如何失败 |
| 输入/输出表示 | 类型、值、对象或元数据，如何与相邻部分连接 |
| 信息与执行阶段 | 哪些信息静态可知，哪些操作运行期执行 |
| 共享规则 | 哪些名称、顺序、约束、所有权或错误语义必须一致 |
| 技巧与证据 | 需要哪些技巧，主要风险是什么，如何验证 |

仅对实际共同需要的信息建立统一表示，例如字段描述或消息类型集合。不预建包揽所有未来功能的中间表示。接口组合困难时重新检查职责和表示，不持续叠加转换层。

## 4. 选择技巧并解释理由

根据 [类型计算](type-computation.md)、[约束与诊断](concepts-and-diagnostics.md)、[常量求值与反射](constant-evaluation-and-reflection.md) 的五项表筛选候选。

先排除语义不匹配、标准不支持或违反项目约束的候选，再比较仍可行的实现。多个子功能可共用一种技巧，同一子功能也可组合多种技巧；无需为每个职责寻找独有技术。

面向当前任务记录：**技巧 → 使用方式 → 场景 → 目的 → 收益**。把抽象技巧落实到具体对象和接口，例如“用 ConstReadable 约束 const 对象的 read 调用”，而不是只写“用 concepts 增强安全性”。补充实际影响选择的代价与替代方案，不强制罗列固定数量的候选。

## 5. 检查适用性、组合和收益

涉及多技巧时读取 [组合边界与案例](technique-composition.md)。检查范围由真实依赖决定，不对每个小函数逐项执行全部检查。

| 主要目的 | 可观察收益 | 判断依据 |
|---|---|---|
| 接口正确性 | 非法类型在适当边界被拒绝 | 正反约束与诊断位置 |
| 减少维护负担 | 一个事实只维护一处，新增类型不需同步修改多个表 | 信息来源和实际修改点 |
| 可扩展性 | 新类型通过稳定接口接入 | 代表性扩展是否需要改无关核心代码 |
| 运行性能 | 减少解析、分派、临时对象或遍历 | 目标负载下测量 |
| 编译成本 | 减少时间、内存或重型实例化 | 相同工具链与输入规模下比较 |

同时考虑诊断、可读性、编译成本、代码体积、依赖与兼容成本。收益可以是类型安全，不必强行转化为性能指标。区分“预期”“原型已观察”“目标环境已验证”，不用无依据打分或默认宣称零成本。

## 6. 对未知项做最小验证

验证应回答明确问题：某组重载是否歧义、某操作是否可常量求值、某引用是否悬空、目标规模是否造成成本增长。复用现有证据；不在缺少关键依据时先建完整框架。

探针失败后先分析原因。缺少头文件不能算成功拒绝非法输入，工具链不支持反射也不能推导功能本身无法由已有元数据实现。只有对任务范围有实际影响时才讨论变更标准或依赖。

## 7. 实施、验证和反馈

按任务权限实施或只输出建议。采用 [验证与成本](verification-and-cost.md) 中与改动有关的证据；大功能覆盖组件交界和相关完整路径。

| 发现 | 回到哪里调整 |
|---|---|
| 实现符合局部规则，却不符合用户行为要求 | 功能契约与职责划分 |
| 单项技巧不支持目标输入 | 候选选择和适用条件 |
| 组件单独成立，组合后错误 | 共享表示、接口与组合边界 |
| 正确但规模成本不满足目标 | 实际热点、静态变化维度及技巧取舍 |
| 环境缺少能力 | 工具链事实及范围内可行方案 |

不通过删除必要约束、添加宽泛兜底或提高资源限制来制造表面通过。完成当前任务所需证据后停止；没有新改动、失败或未解决风险时不继续扩大测试。

## 8. 按规模交付

局部问题可以用一段话；大功能可用职责/技巧表。说明功能与环境、五项选型解释、必要组合关系、代价和未解决项，以及匹配任务阶段的验证计划或实际结果。

例如：输入类型静态已知，函数体需要对 const 对象执行 read，因此用命名 concept 表达接口条件。函数体无需类型分类，当前不增加 if constexpr。预期收益是在接口边界拒绝不支持的类型；用可读、仅可变对象可读和重载选择用例验证。

解释和方案任务完成相应交付即可，不要求实际修改项目才能结束；选型结论也不扩大用户授权范围。
